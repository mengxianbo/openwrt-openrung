# OpenRung Go dependency license audit

## Audited build target

The OpenWrt client is built from the upstream Go package `./cmd/client` with:

- `GOOS=linux`
- `GOARCH=amd64`
- `CGO_ENABLED=0`
- build tags `with_utls,with_external_windivert`
- Go toolchain `1.25.5`

For historical Build #24, the exact upstream commit is
`5cba4f0b9da642dcc9cc1904f861eb1d59c23a04`. Its exact `go.mod` and
`go.sum` are in the corresponding-source archive. The module graph includes
direct and indirect requirements; the compiled package list generated by
`go list -deps` is the narrower target-specific view. These are deliberately
reported separately and must not be conflated.

## Automated workflow

`.github/workflows/go-license-audit.yml`:

1. Can be manually dispatched against an exact upstream ref; its default is
   the historical #24 upstream commit.
2. Runs automatically after a successful `Build OpenRung OpenWrt IPK` run and
   extracts the exact upstream commit from the IPK's `SOURCE-INFO.txt`.
3. Runs the target-specific dependency/license scan with the pinned
   `google/go-licenses` v2.0.1 tool.
4. Produces the CSV license report, compiled Go package list, complete Go
   module graph, tool output, and collected license files as a separate
   90-day Actions artifact.
5. Fails the audit for classifier categories `forbidden`, `restricted`, or
   `unknown`. A report is not a legal opinion; any tool warnings, non-Go
   code, generated assets, patent/trademark terms, NOTICE obligations, and
   special license terms still require human review.

The audit is a separate post-build workflow. It does not edit source code,
change dependencies, rebuild or replace IPKs, or publish release assets.

## Interpretation and limits

- `go.mod` / `go.sum` describe the pinned module graph and integrity hashes;
  they do not by themselves prove which modules are linked into the binary.
- `go list -deps` under the exact target, platform, and build tags records the
  selected Go package graph.
- `go-licenses` classifies licenses it can identify and collects license
  texts/notices. Classifier output must be reviewed against each dependency's
  actual source and version.
- Go assembly, C/C++ code, embedded data, prebuilt binaries, and other native
  assets may carry obligations outside the Go package scan.
- GPL obligations arising from the statically linked sing-box dependency are
  expected for this upstream client and must not be treated as an unexpected
  license failure merely because they are copyleft.
- Passing automation means the tested target produced no disallowed/unknown
  classifications; it does not certify complete legal compliance.


## Existing #24 vendor snapshot (source artifact inspection)

The preserved #24 corresponding-source artifact was inspected without
modifying it. Its upstream `vendor/modules.txt` contains **211 module entries**
and the vendor tree contains **218 LICENSE/COPYING/NOTICE-style files**.
This confirms that the archived dependency source tree and a substantial set
of license texts are present. It is not the final count of modules linked into
the Linux client: `go mod vendor` can include dependencies used by other
upstream packages as well. The target-specific `compiled-go-packages.txt`
and `go-licenses.csv` generated by the new audit workflow are the evidence
to use for the actual `./cmd/client` dependency set.
